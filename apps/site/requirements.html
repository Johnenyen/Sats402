Bounty Requirement 01

SDK for Agent Payments

“SDK for agent-to-agent and agent-to-service payments”
How Sats402 meets it

We built a complete, production-ready TypeScript/JavaScript SDK modularized across the @sats402/* package family: @sats402/agent, @sats402/core, @sats402/express, and @sats402/verify, alongside the standalone sats402 CLI. The SDK exposes an autonomous agent fetch client (@sats402/agent) with spending policies (per-call caps, session budgets, and payee allowlists) and automated 402 challenge negotiation, alongside zero-custody paywall middleware (@sats402/express). The agent-to-agent case is two independent key-holders—each running the agent client and paywall—where one agent signs and broadcasts its own tachi_tx on-chain to pay the other.

Bounty Requirement 02

Standard x402 Protocol Support

“Support for x402 / pay-per-request pattern”
How Sats402 meets it

Sats402 implements the standard x402 pay-per-request protocol using the exact payment scheme bound to Tachi (formal specification in specs/schemes/exact/scheme_exact_tachi.md). The protocol uses exactly the three standard x402 v2 HTTP headers: PAYMENT-REQUIRED on HTTP 402, PAYMENT-SIGNATURE on the paid retry, and PAYMENT-RESPONSE on HTTP 200. Every service endpoint is documented with OpenAPI 3.1 definitions (/openapi.json) detailing the 402 challenge response, required payment schemas, and x-sats402 metadata.

Proof

Every paid call adheres strictly to the pay-per-request lifecycle. Requests pay per call, exactly per spec, with zero accounts, zero API keys, and zero subscriptions:

1

402 Payment Required: Service challenges unauthenticated requests with HTTP 402 carrying the base64-encoded PAYMENT-REQUIRED header (network tachi:0f9188f13cb7b2c71f2a335e3a4fc328, scheme exact, amount in atomic sat units, payee x-only public key, timeout, and transfer method tachi_tx).

2

Cryptographic Binding & Settlement: Client settles the requested sats on-chain, binds the challenge parameters (URL, nonce, payee, network, amount) with its BIP-340 Schnorr key, and retries the HTTP request with the base64-encoded PAYMENT-SIGNATURE header.

3

200 OK + Settlement Receipt: Service verifies the signature and confirms on-chain settlement with the Tachi daemon, serving the paid resource with the base64-encoded PAYMENT-RESPONSE header.

Strict spec compliance verified: Tampered or incorrect payments (e.g. paying 49 sats against a 50-sat challenge) trigger immediate 402 invalid_payment_requirements rejection with zero second charge. Duplicate requests are handled with replay protection keyed by network:txhash.

Bounty Requirement 03

Native Sats Settlement on Tachi

“Native sats settlement on Tachi”
How Sats402 meets it

Payments settle in native satoshis directly on Tachi (network identifier tachi:0f9188f13cb7b2c71f2a335e3a4fc328 on tachi-regtest-1) via agent-signed, agent-broadcast tachi_tx transactions. The paying agent retains absolute sovereignty: its private key signs the transaction, and the agent broadcasts directly to the Tachi daemon (https://rpc-regtest.tachibtc.com). The verifier and paywall middleware hold zero private keys and custody no funds, acting purely as a read-only verifier of on-chain state.

Bounty Requirement 04

Example Application

“Example app (agent paying for API/model/data/service)”
How Sats402 meets it

We built a complete, one-command example application runnable via npm run cold-start (source in demo/cold-start.mjs), supported by an interactive web demo at /demo and a CLI runner (npm run demo:pay). In the demo app, an autonomous agent queries an inference agent (S2) with a complex prompt; before answering, S2 autonomously purchases live fee telemetry from a daemon data service (S1), grounds its reasoning in the fresh facts, and serves the answer back to the buyer agent. The app tests multi-hop agent commerce, a 20-call paid burst, and defensive policy boundaries.

Cold-Start Demo Loop

The loop runs in demo/cold-start.mjs exactly as it executes:
1. Agent asks S2 a question. S2 cannot answer yet: it needs live network state.
2. S2 pays S1 (5 sats): the inference agent autonomously buys the live daemon fact before answering (agent-to-service).
3. Agent pays S2 (50 sats): S2 delivers the grounded completion, where two independent key-holders settle on-chain with the buyer signing and broadcasting a tachi_tx to pay S2.
4. Burst (20 calls): Agent reads S1 directly per call, each a separate paid request (agent-to-service).
