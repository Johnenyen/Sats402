Protocol documentation

How Sats402 works, end to end.

Sats402 implements the x402 pay-per-request pattern with settlement in native sats on Tachi. This page is the protocol. The normative network binding lives in specs/schemes/exact/scheme_exact_tachi.md.

The flow

1 · AskThe agent requests a resource. No payment yet.
2 · 402The service refuses and sends a challenge: price in sats, payee key, network, validity window.
3 · PayThe agent signs and broadcasts its own tachi_tx, paying the exact amount to the payee's owner key. The sats move on-chain.
4 · ProveThe agent retries with the settlement proof. The service re-fetches the transaction from the daemon, sees committed funds, and serves the resource.
The service holds no key and moves no funds. Every settlement is a tx id on Tachi: daemon-returned and re-fetchable by anyone.

Wire format

Three x402 v2 headers, nothing more:

PAYMENT-REQUIREDOn the 402 response. Carries the challenge: price in sats, payee, network, validity window. Base64 JSON.
PAYMENT-SIGNATUREOn the paid retry. Carries the payment payload: signature, authorization, and the settlement proof. Base64 JSON.
PAYMENT-RESPONSEOn the successful 200. Carries the settlement response for the client's records.

Payment scheme

Sats402 uses the exact scheme with a Tachi network binding, written from the x402 scheme template specification.

Network identifiersCAIP-2-style in the tachi namespace, reference taken from the underlying Bitcoin network's genesis prefix (BIP-122 convention). Example: tachi:0f9188f13cb7b2c71f2a335e3a4fc328 (tachi-regtest-1). The namespace is a proposal declared by this binding.
AmountsSat strings. Atomic units. Exact match required: no rounding, no fees added, no tolerance.
PayeeThe payee's x-only owner key on the Tachi ledger. The same key owns the received output.
BindingThe payer's signature covers the complete challenge and settlement: network, amount, payee, resource, nonce, validity window, and settlement transaction hash. A payment made for one request cannot be presented for another. Resource URLs are normalized on both sides before binding.

Settlement

The client settles: it signs and broadcasts its own tachi_tx, paying the exact requested amount to the payee's owner key. The service verifies by reading the daemon: the transaction exists, is committed, and the amount and payee match the challenge. The key that owns the spent sats is the key that signed. Verification needs no keys and no wallet.

Replay protection

Each settlement is consumed once, keyed by network + ":" + tx_hash. Replay protection is restart-durable only when backed by an external persistent store (such as Vercel KV or Upstash/Redis); without an external store, durability is strictly in-process and bounded by instance lifetime. A settlement is never charged twice: a retry with the same proof returns the original response while the server still holds it (marked X-Sats402-Replayed: 1), and is rejected otherwise.

Verifying a settlement

Three ways, all read-only, none needing keys:

WebPaste the tx id on the verify page, or open GET /receipt/<txid> for JSON.
CLInode packages/cli/bin/sats402.mjs verify <txid> [--payee <key>] [--amount <sats>]
Library@sats402/core/verify — a keyless subpath: key material is excluded by construction, safe for verifiers and paywalls.

Errors

402 invalid_payment_requirementsWrong amount, wrong payee, or wrong network. Nothing is served.
402 invalid_payment_payloadThe payment is not bound to this request (URL, nonce, or resource mismatch).
402 invalid_signatureThe signature does not verify against the payer's key.
402 replay_detectedThis settlement was already consumed.
500 verification_unavailableThe daemon could not be read. Transient: retry. No settlement is consumed.

Quickstart

A paid endpoint (Node, any framework via the middleware):

import { paywall, FileReplayStore } from '@sats402/express';

export default paywall({
  priceSats: 5n,
  payeeXOnly: process.env.PAYEE_XONLY,
  publicBaseUrl: 'https://sats402.vercel.app',
  replay: new FileReplayStore('/var/lib/sats402/replay.jsonl'),
  serve: (req, res) => res.end(JSON.stringify({ hello: 'paid' })),
});

An agent that pays (discover the payee from the challenge, then allow it):

import { Sats402Agent } from '@sats402/agent';
import { deriveIdentity, NETWORK_TACHI_REGTEST } from '@sats402/core';

const DAEMON = 'https://rpc-regtest.tachibtc.com';
const url = 'https://sats402.vercel.app/api/services/price';

// Discover the payee from the 402 challenge with a plain call.
const probe = await fetch(url);
const challenge = JSON.parse(atob(probe.headers.get('payment-required')));
const payTo = challenge.accepts[0].payTo;

const agent = new Sats402Agent({
  identity: deriveIdentity(MNEMONIC, 'regtest', 0),
  daemonUrl: DAEMON,
  network: NETWORK_TACHI_REGTEST,
  policy: { perCallCapSats: 60n, sessionBudgetSats: 400n,
            payeeAllowlist: [payTo] },
});
const res = await agent.fetch(url);
// 402 handled, tachi_tx settled, proof retried. Product in res.

Direct agent-to-agent payment (agent.pay):

// Direct agent-to-agent settlement: one key-holder paying another, verified read-only
const { txHash, receipt } = await agent.pay({
  payeeXOnly: '99296e2fdf89f7249584f5572829f32e52e1e780e64743ed75601e7c6acf512e',
  amountSats: 50n,
  memo: 'agent task completion',
});
// Verified read-only: txHash is on-chain, policy checked, receipt returned.
Runnable examples: npm run demo:pay -- inference (the agent on your machine) and npm run cold-start (the full recorded loop). Source: github.com/Johnenyen/Sats402.
